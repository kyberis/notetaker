# confirm-before-write

> Will never deletes a note on his own say-so. He describes the deletion, shows
> a Delete / Keep card, and only removes the note once the user taps Delete.

## What it does

Asking Will to delete a note used to remove it immediately. The model decided,
alone, that the user had confirmed — the `deleteNote` tool took a `confirm: true`
argument that the model itself set, so it was a confirmation in name only.

Now the tool describes the deletion instead of performing it. The user gets a
card showing which note is at stake, with two buttons. The note survives until
Delete is tapped. If nobody taps, the request expires after 15 minutes and the
note stays.

Available in all four agent languages (en / es / pt / ar).

## Data model

`AgentProposal` holds one pending write:

| Field | Notes |
|-------|-------|
| `id` | Generated by `@kyberis/agent-os/safety`, 11 chars of base64url. Short because Telegram caps `callback_data` at 64 bytes. |
| `userId` | Owner. Cascade-deleted with the user. |
| `conversationExternalId` | Telegram chat the card was sent to. |
| `kind` | `deleteNote` today. |
| `dataJson` | The validated payload, re-validated on confirm. |
| `summary` | Card summary, capped at 500 chars. |
| `status` | `PENDING` → `CONFIRMED` / `CANCELLED` / `EXPIRED`. |
| `expiresAt` | 15 minutes after creation. |

## Contracts

**Agent tool** — `deleteNote({ id })`. No `confirm` argument: there is nothing
the model can set that would make the write happen. Returns
`{ proposed: true, proposalId }`, or `{ proposed: false, reason }` when the note
does not exist or the channel cannot collect a confirmation.

**Telegram** — the card goes out after the agent's prose, with an inline
keyboard of `p:<id>:y` and `p:<id>:n`. A tap arrives as `callback_query` and is
handled before the agent is ever invoked, so a confirmation costs no quota and
runs no model.

**Agent loop** — `runNoteAgent` takes an optional `onProposal` and returns
`proposals` alongside the text. Callers that do not pass `onProposal` get an
agent that cannot delete; it never falls back to writing.

## Invariants

- No note is deleted without a `callback_query` carrying that proposal's id.
- A proposal applies at most once. `confirm` on an already-confirmed row is a
  no-op that reports success.
- The confirming user must own the proposal **and** be in the chat it was raised
  in. `callback_data` is client-supplied and ids are short, so neither is
  assumed.
- The stored payload is re-validated on confirm. It was produced by a model and
  may be 15 minutes old.
- An expired proposal is marked `EXPIRED` rather than applied.
- The card is edited into its result after a tap, so the buttons cannot be used
  twice.

## Known gaps / TODOs

- Only `deleteNote` is behind confirmation. `updateNote` can still rewrite a
  note body outright, which is destructive in a quieter way and should probably
  follow.
- Nothing purges `AgentProposal` rows yet. `proposalStore.purgeExpired()` exists
  but no cron calls it, so expired rows accumulate. Add it to the daily
  `account-purge` job.
- The web app has no confirmation UI, which is fine while it stays read-only.
- The 15-minute TTL is the package default and has not been tuned against real
  usage.
